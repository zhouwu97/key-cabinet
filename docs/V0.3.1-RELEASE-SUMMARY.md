## 🎯 核心目标

在进入 `v0.4.0-backend-integrated` 之前，**系统性对齐前端代码与后台协议文档**，避免后端开发时出现数据契约不一致导致的返工。

---

## ⚠️ 发现的主要问题

### 问题1: BorrowRecord 状态机完全不同 (P0)

**前端代码** (已通过 24 项测试):
```typescript
BORROWING | BORROWED | RETURNING | COMPLETED | EXCEPTION
```

**文档定义** (会导致后端实现不兼容):
```typescript
BORROWED | RETURNED_NORMAL | OVERDUE | RETURNED_OVERDUE | LOST
```

### 问题2: DeviceOperation 混淆了状态和事件 (P0)

**前端代码** (清晰分离):
```typescript
// 生命周期状态
status: CREATED | AUTHORIZED | SENT | EXECUTING | SUCCESS | FAILED | TIMEOUT | CANCELLED

// 设备事件流
events: [POSITIONING, POSITIONED, DOOR_OPEN, KEY_REMOVED, RFID_CONFIRMED, ...]
```

**文档定义** (混为一谈):
```typescript
status: INIT | PREPARING | DOOR_OPENED | VERIFYING | COMPLETED | FAILED
```

### 问题3: Reservation 缺少关键状态 (P0)

**前端代码** (支持预约未来时间):
```typescript
PENDING | APPROVED | ACTIVE | USED | REJECTED | CANCELLED | EXPIRED
```

**文档定义** (缺少 APPROVED):
```typescript
PENDING_APPROVAL | ACTIVE | USED | CANCELLED | EXPIRED | REJECTED
```

### 问题4: 枚举不完整 (P1)

- **KeyPresenceState**: 文档只有 `PRESENT | ABSENT`，代码还有 `UNKNOWN | FAULT`
- **DeviceStatus**: 文档用 `ERROR`，代码用 `FAULT | MAINTENANCE` (语义更清晰)

### 问题5: Auth API 缺失 (P0)

后台开发必需的 `POST /auth/wechat-login` 完全没有定义。

### 问题6: HTTP 状态码模糊 (P1)

文档写"HTTP 200 或 4xx/5xx"，后台开发者不知道该返回哪个。

### 问题7: 实时更新策略未定 (P1)

文档写"SSE / Polling"，未明确 v0.4 应该用哪个。

---

## ✅ 解决方案

### 1. 统一状态机 (以代码为准)

| 实体 | 最终统一枚举 |
|:---|:---|
| `BorrowRecordStatus` | `BORROWING`, `BORROWED`, `RETURNING`, `COMPLETED`, `EXCEPTION` |
| `DeviceOperationStatus` | `CREATED`, `AUTHORIZED`, `SENT`, `EXECUTING`, `SUCCESS`, `FAILED`, `TIMEOUT`, `CANCELLED` |
| `ReservationStatus` | `PENDING`, `APPROVED`, `ACTIVE`, `USED`, `REJECTED`, `CANCELLED`, `EXPIRED` |
| `KeyPresenceState` | `PRESENT`, `ABSENT`, `UNKNOWN`, `FAULT` |
| `DeviceStatus` | `ONLINE`, `OFFLINE`, `BUSY`, `FAULT`, `MAINTENANCE` |
| `Key.status` | `AVAILABLE`, `RESERVED`, `BORROWED`, `MAINTENANCE`, `DISABLED` (移除 `OVERDUE`) |

### 2. 明确派生逻辑

**逾期判断**:
```typescript
// 当前是否逾期 (实时计算)
isOverdue = status === 'BORROWED' && now > expectedReturnAt

// 历史是否曾逾期 (从字段判断)
wasOverdue = status === 'COMPLETED' && overdueAt != null

// 前端显示
归还结果 = wasOverdue ? "逾期归还" : "按时归还"
```

### 3. 补充 Auth API

```http
POST /api/v1/auth/wechat-login

Request:
{
  "code": "wx.login() 返回的临时 code"
}

Response:
{
  "accessToken": "...",
  "expiresIn": 7200,
  "user": { "id", "name", "role" }
}
```

### 4. 明确 HTTP 状态码

```text
200/201   成功
400       参数错误
401       未登录/Token失效
403       无权限
404       实体不存在
409       状态冲突/预约冲突/设备忙
422       业务条件不满足
500       服务端异常
503       设备离线/服务不可用
```

### 5. 确定实时更新策略

- **v0.4**: HTTP Polling (每 1~2 秒查询一次)
- **v0.5+**: WebSocket 推送

### 6. 架构决策

**V1 不支持无预约直借**:
```text
V1: Reservation ACTIVE + Identity verified → 允许 PICKUP
V2 (规划): 支持无预约现场直借
```

### 7. DTO 层设计指南

创建 `DTO-DESIGN-GUIDE.md`，规范前端如何处理 ISO 时间 ↔ number 时间戳转换。

## 💡 关键收获

### 为什么会出现不一致？

1. **时间差**: 文档在 Stage 2 早期编写，代码在 Stage 3 持续演进
2. **缺少反向验证**: 文档"冻结"后未与实际代码对比
3. **测试盲区**: 自动化测试只验证 Mock 层，未暴露文档问题

### 如何避免未来不一致？

1. **代码即文档**: 后续状态机优先从代码生成文档
2. **契约测试**: v0.4 引入契约测试，自动验证 API 响应与 DTO 一致
3. **定期审查**: 每个大版本前人工审查协议文档与代码一致性
