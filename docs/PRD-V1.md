# 智能钥匙借还微信小程序 V1 设计方案（PRD）

> 本文档为小程序 V1 需求与架构的唯一依据。原论文交互（矩阵键盘输入密码/工号/电话/房间号，单片机控制步进电机、电磁锁、转盘）迁移到手机端：身份输入、钥匙选择、借还记录、状态展示全部由小程序承载，柜体只负责执行。

## 一、项目定位

项目暂定：**智能钥匙借还微信小程序**

小程序负责三件核心事情：

```text
人是谁
   ↓
想借哪把钥匙
   ↓
设备有没有成功完成操作
```

整个小程序定义：**用户身份管理 + 钥匙借还业务 + 设备操作界面 + 借还记录 + 异常处理。**

小程序**不负责**（统一视为设备端能力）：

```text
步进电机转多少度
GPIO怎么控制
红外传感器怎么读取
电磁锁如何驱动
ESP怎么控制单片机
RK3588内部算法
```

## 九、钥匙状态

完整枚举：

```text
AVAILABLE    可借
RESERVED     已预约
PENDING      审批中
BORROWED     借出
OVERDUE      逾期
MAINTENANCE  维护
LOST         遗失
DISABLED     停用
```

小程序只根据状态渲染，例如：

```text
AVAILABLE   → 申请借用
PENDING     → 审批中
BORROWED    → 已借出
MAINTENANCE → 暂停使用
```

## 十一、借钥匙流程

```text
钥匙详情 → 申请借用 → 填写用途 → 填写预计归还时间 → 提交
→ 审批 → 批准 → 到钥匙柜 → 扫码 → 执行取钥
```

不是"点击按钮 → 柜子直接开"。这样权限、安全和记录都好处理。

## 十三、借用订单

整个项目核心不是"钥匙"，而是 **BorrowOrder 借用订单**。每次借钥匙建立一条订单：

```json
{
  "id": "BO202609020001",
  "userId": "U001",
  "keyId": "KEY103",
  "deviceId": "CAB001",
  "status": "WAITING_PICKUP",
  "purpose": "实验",
  "expectedReturnAt": "2026-09-02T18:00:00"
}
```

## 十七、设备事件



## 二十、归还流程

```text
首页 → 当前借用 → 归还钥匙 → 扫描钥匙柜 → 确认设备 → 开始归还
→ 设备定位 → 柜门打开 → 放入钥匙 → 传感器确认 → 柜门关闭 → 完成
```

最关键：**用户点击"已放回"不能直接代表归还成功**，必须等设备反馈 `KEY_RETURNED`，订单才置为 `COMPLETED`。

## 三十、最关键的一层：DeviceService

页面不要直接 `mqtt.publish(...)`，应该 `deviceService.borrowKey(...)`：

```typescript
borrowKey(deviceId, keyId)
returnKey(deviceId, keyId)
getDeviceStatus(deviceId)
subscribeDevice(deviceId)
```

内部现在可以 MQTT，以后老师突然说改后端 API，只改 DeviceService，UI 完全不用动。

## 三十一、通信层设计

V1：

```text
小程序 → MQTT over WebSocket → MQTT Broker → ESP
```

Topic：

```text
keybox/{deviceId}/command
keybox/{deviceId}/event
keybox/{deviceId}/status
keybox/{deviceId}/heartbeat
```

## 三十二、取钥消息

```json
{
  "version": "1.0",
  "requestId": "REQ001",
  "action": "BORROW",
  "keyId": "KEY103",
  "timestamp": 1788342000
}
```

设备回复：

```json
{
  "version": "1.0",
  "requestId": "REQ001",
  "event": "POSITIONING",
  "timestamp": 1788342001
}
```

最终：

```json
{
  "version": "1.0",
  "requestId": "REQ001",
  "event": "SUCCESS",
  "timestamp": 1788342015
}
```

## 三十三、requestId 必须有

用户疯狂点击 3 次不能开柜 3 次。每次业务操作必须有 `requestId`（例如 `REQ-20260902-00001`），设备端应识别重复请求。

## 三十四、设备在线状态

ESP 每 5~10 秒发送心跳：

```json
{
  "deviceId": "CAB001",
  "status": "IDLE",
  "timestamp": 1788342000
}
```

小程序显示 `● 在线`；超过一定时间没有心跳显示 `○ 离线`。真正上线以后，最好由服务端判断，不让客户端自己决定。

## 三十五、本地开发一定做 Mock 模式

没有 ESP 也可以把整个小程序写完。开发环境 `USE_MOCK=true`，点击借钥匙后模拟：

```text
500ms  → RECEIVED
1500ms → POSITIONING
3000ms → DOOR_OPEN
5000ms → KEY_REMOVED
6500ms → SUCCESS
```

把 UI、状态机、页面流程、错误处理全部开发完成，等 ESP 好了 `USE_MOCK=false` 接 MQTT。这就是团队并行开发。

## 三十六、UI 风格建议

不做赛博朋克 / 大量渐变 / 玻璃拟态 / 花里胡哨动画。钥匙管理本质是工具类：**简洁、可靠、明确**。

```text
白色背景
浅灰页面底色
蓝色 = 主操作色
绿色 = 正常
橙色 = 等待
红色 = 异常
```

卡片轻圆角即可，不要超大圆角、复杂阴影、悬浮渐变球。

## 三十七、页面的设计原则

所有设备操作页面必须让用户清楚知道：

```text
现在发生了什么 → 需要我做什么 → 成功没有
```

不要"正在处理..."，而要"柜门已打开，请取走103实验室钥匙。检测到钥匙取出后将自动完成。"

## 三十八、异常必须提前设计

第一版至少测试这 10 个场景：

| 场景           | 小程序行为       |
| ------------ | ------------- |
| ESP离线        | 禁止操作         |
| MQTT断线       | 提示通信异常       |
| 电机定位失败      | 显示设备故障        |
| 柜门打不开       | 操作失败          |
| 用户没有取钥      | 保持等待          |
| 用户取钥后门没关    | 提醒关闭          |
| 重复点击        | 只执行一次         |
| 操作超时        | 查询最终状态        |
| 用户扫错柜子      | 禁止执行          |
| APP切后台      | 恢复后继续查询状态     |

## 三十九、未完成操作的恢复

用户点击"开始取钥"后退出小程序，不能导致订单消失。回来之后应该：

```text
检测到未完成操作

103实验室钥匙
正在等待设备结果

[继续查看]
```

设备操作状态不能只存在页面变量里，至少存 `activeOperation`，最好以后放服务端。

待审批、审批、钥匙列表、借还记录、设备状态。

## 四十三、开发顺序

不要按页面编号开发。

1. **第一阶段**：先写数据和状态（User / Key / BorrowOrder / Device / Operation）
2. **第二阶段**：Mock DeviceService（borrow / return / status / event）
3. **第三阶段**：核心页面（首页、钥匙列表、详情、申请、设备操作、记录）
4. **第四阶段**：做扫码
5. **第五阶段**：接真实 MQTT
6. **第六阶段**：接后端/API

这样不会被硬件进度卡住。

## 四十四、整个团队的接口边界

只要求设备组满足：

```text
输入：deviceId / keyId / action / requestId
输出：requestId / event / errorCode / timestamp
```

设备内部是 ESP32、ESP → 51、还是 ESP → RK3588 → STM32，与小程序无关。这就是最重要的架构隔离。
