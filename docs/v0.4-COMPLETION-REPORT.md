| 项目 | 方案 | 理由 |
|------|------|------|

| ORM | **GORM** | 支持事务、`FOR UPDATE`、PostgreSQL 特性 |

#### Migration 000002: 预约时间冲突约束

**这是本次后端设计的技术亮点**：

```sql
ALTER TABLE reservations
ADD CONSTRAINT reservations_no_overlap
EXCLUDE USING gist (
  key_id WITH =,
  tstzrange(start_time, end_time) WITH &&
);
```

**原理**：
- PostgreSQL 的 `tstzrange` 类型表示时间范围
- `EXCLUDE USING gist` 创建排他约束
- `key_id WITH =` 确保同一把钥匙
- `tstzrange(...) WITH &&` 确保时间范围不重叠

**效果**：
- 数据库层面直接阻止时间冲突的预约
- 无法通过应用层 bug 绕过
- 并发请求只有一个能成功
- 比纯应用层检查更可靠

### 4. 设备网关设计

#### 接口定义 (`internal/infrastructure/device/gateway.go`)
```go
type DeviceGateway interface {
    StartPickup(ctx context.Context, cmd DeviceCommand) error
    StartReturn(ctx context.Context, cmd DeviceCommand) error
    GetDeviceStatus(ctx context.Context, deviceID string) (*DeviceStatusInfo, error)
    RegisterEventHandler(handler DeviceEventHandler)
}

type DeviceEventHandler interface {
    OnPickupSuccess(ctx context.Context, event DeviceEvent) error
    OnPickupFailed(ctx context.Context, event DeviceEvent) error
    OnReturnSuccess(ctx context.Context, event DeviceEvent) error
    OnReturnFailed(ctx context.Context, event DeviceEvent) error
}
```

**设计亮点**：
- **命令与事件分离**：`StartPickup` 发送命令，`OnPickupSuccess` 接收事件
- **异步回调机制**：设备操作完成后通过回调通知业务层
- **v0.4 Mock 实现**：100ms 后自动触发成功事件
- **v0.5 MQTT 实现**：真实 MQTT 消息触发事件
- **业务代码无感知**：`OperationService` 不关心底层是 Mock 还是 MQTT

## 关键技术决策

### 1. 为什么选择 PostgreSQL 而不是 MySQL？

**决定性因素**：预约时间冲突检测

MySQL 方案：
```sql
-- 应用层检查
SELECT * FROM reservations
WHERE key_id = ? AND status = 'ACTIVE'
  AND ((start_time < ? AND end_time > ?)
    OR (start_time < ? AND end_time > ?))
FOR UPDATE;

-- 手动判断冲突
-- INSERT
```

PostgreSQL 方案：
```sql
-- 数据库约束自动拒绝
INSERT INTO reservations (...) VALUES (...);
-- 如果时间重叠，自动返回 CONFLICT 错误
```

**优势**：
- 并发安全：数据库层面保证，无法绕过
- 代码简洁：不需要复杂的应用层锁
- 性能更好：避免长事务锁

### 2. 为什么要分 User 和 UserIdentity 表？

**设计目标**：支持多种登录方式

```
User (U001)
  ├─ UserIdentity (WECHAT, openid_xxx)
  └─ UserIdentity (FACE, face_profile_001)
```

**好处**：
- v0.4: 微信登录
- v0.6: 人脸识别登录（RK3588）
- 未来: 学号密码登录、指纹登录
- 所有方式最终指向同一个 User

### 3. 为什么 DeviceGateway 要用事件回调而不是同步返回？

**原因**：设备操作是异步的

取钥流程：
```
1. Backend 发送命令 → 设备
2. 设备接收命令
3. 设备执行（开锁、等待取出、关锁）
4. 设备返回结果 → Backend
```

这个过程需要 3-10 秒。

**同步方案的问题**：
```go
err := gateway.StartPickup(...)  // 阻塞 3-10 秒？
```
- HTTP 请求超时
- 占用连接资源
- 无法处理中间状态

**事件回调方案**：
```go
// 1. 立即返回
err := gateway.StartPickup(...)  // 立即返回

// 2. 设备完成后回调
func (s *OperationService) OnPickupSuccess(event) {
    // 更新数据库状态
    // 通知小程序（轮询/WebSocket）
}
```

**优势**：
- HTTP 请求立即返回
- 支持长时间操作
- 统一处理成功/失败
- Mock 和 MQTT 实现一致

### 4. 为什么不全靠 GORM AutoMigrate？

**GORM AutoMigrate 的限制**：
- 无法创建 PostgreSQL 特定约束（`EXCLUDE`）
- 无法管理复杂索引
- 没有版本控制
- 无法回滚

**SQL Migration 的优势**：
```
migrations/
├── 000001_init.up.sql          # 创建表
├── 000001_init.down.sql        # 删除表
├── 000002_reservation_constraint.up.sql    # 添加约束
├── 000002_reservation_constraint.down.sql  # 删除约束
```

- 版本化管理
- 支持所有 SQL 特性
- 可以回滚
- 适合生产环境

**实际使用**：
- Migration: 表结构、约束、索引
- GORM: CRUD、事务、`FOR UPDATE`
